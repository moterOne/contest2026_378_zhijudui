# 阶段 B：ESP32-P4X-Function-EV-Board 基础板级外设实施步骤

本文细化 [`openvela-板级适配实现方案.md`](./openvela-板级适配实现方案.md) 的阶段 B。目标是在[阶段 A 最小可启动配置](./openvela-阶段A-最小可启动配置实施步骤.md)已通过的基础上，逐项接入并验证 GPIO、按键候选、MicroSD、USB 和以太网。**这是实施清单，不是已实现或已通过验证的功能清单。** 当前工作树仍缺 ESP32-P4 芯片级支持，且阶段 A 的占位板级代码尚未完成；未取得稳定可交互的 NSH 基线时，阶段 B 全部标记为“阻塞”。

## 0. 放行条件与范围

- 保存阶段 A 的工作树版本/上游依赖版本、板卡和 PCB 版本、defconfig、构建命令、映像及烧录方法、串口接法、冷启动和复位日志。每一项外设的结果均以此作为对照，不能牺牲启动或 NSH 控制台换取外设可用。
- 板级代码仅在 `contest2026_378_zhijudui/board/contest_board/` 内维护；manifest 已映射到 `vendor/openvela/boards/contest2026_378_board/`，不要直接编辑目标目录。芯片控制器或公共驱动缺失时，记录阻塞并按公共仓库的独立上游流程处理；不要复制其他 ESP32 芯片驱动冒充 P4 支持。
- 以 **ESP32-P4X-Function-EV-Board 对应 PCB 版本的参考设计、原理图/BOM、芯片手册及当前集成源码**为电气与软件依据。本目录的 MinerU 文本只提供组件概述和 J1 排针信息，不能代替完整引脚表、PHY 地址、供电/复位拓扑或 USB 连接图。
- 首轮仅选 **一个功能**修改配置、板级初始化和测试，不一次启用全部外设。每项测试前确认独立供电、GPIO 电压、引脚占用、相关 VDD 电源域及 `LDO_VO3/LDO_VO4` 的使能/电压/上电顺序；没有依据则停在核查阶段。
- 本阶段不包括 ESP32-C6 Wi-Fi/蓝牙、ES8311/NS4150 音频、MIPI-DSI/CSI、触摸或 H.264。C6 的存在不代表 P4 已具备无线驱动或固件通信协议。

## 1. 建立“每项外设一张卡”的实施循环

每个候选功能按下表填记录，未填全前不改板级配置：

| 字段 | 必须回答的问题 |
| --- | --- |
| 硬件依据 | 板卡 PCB 版本及对应原理图页号、器件和接口；引脚、复用、上拉/下拉、有效电平、供电和复位是谁负责？ |
| 软件依据 | 当前 P4 芯片控制器驱动、NuttX 子系统驱动、Kconfig 符号和初始化 API 是否确实存在？来源/版本？ |
| 资源冲突 | 是否与 NSH UART、启动管脚、Flash、板载 C6、其他已接外设或 USB 共享资源冲突？ |
| 接入点 | 所选 Make/CMake 构建路径中哪个板级文件编译，哪个启动入口调用；初始化依赖时序与错误如何处理？ |
| 测试 | 实际设备节点/网络接口/主机枚举结果、无破坏性测试步骤及通过标准；失败日志保存位置？ |
| 回归 | 冷启动、复位、NSH 输入输出、已验证外设均是否保持正常？ |

对每个功能执行相同流程：① 查硬件和驱动 → ② 只新增本功能所需的板级配置及源文件 → ③ 生成配置并确认选项未被消解 → ④ 按阶段 A **已验证的**构建/烧录路径生成测试映像 → ⑤ 实机验证 → ⑥ 冷启动、复位及 NSH 回归 → ⑦ 在 README/测试记录中标记通过、失败或阻塞。测试失败先恢复该功能的板级变更并证明基线仍能工作，再调查原因。不要因功能缺失而硬编码未知 GPIO、IRQ、PHY 地址或电压。

板级初始化只注册本板确有的设备；优先使用已确认的晚期初始化/bring-up 路径，在调度器、控制器、时钟及电源就绪之后执行。若某功能必须更早接入，要沿 P4 启动调用链确认时序。可选外设失败应保存返回码与设备名，并按其启动依赖决定是否让 NSH 继续运行；不能默默吞掉错误，也不能让未插卡、未接网线等正常缺席状态使整机不可启动。

## 2. GPIO：先外接受控负载

1. 从 P4X 对应原理图和 J1 表挑选**未被板载器件、启动管脚或控制台占用**的一路 GPIO。记录 J1 针脚与 GPIO 号的映射、允许电压/驱动能力、复用和上电默认状态。J1 列出 GPIO37/U0TXD、GPIO38/U0RXD；若它们用于阶段 A 控制台，**不得**作为 GPIO 测试脚。不要把 5 V 电源针脚连接到 GPIO。
2. 先确认当前芯片 GPIO 控制器、GPIO character driver 或适用板级接口已存在；按已选构建路径只为该测试引脚新增配置、引脚定义、设备注册及必要的安全初值。驱动不存在则标记阻塞，不在板级目录伪造芯片寄存器驱动。
3. 使用限流且符合 GPIO 电压的外接测试负载或电平测试仪，验证输出高/低及复位后的初始状态；再用受控 3.3 V 输入验证读取（若支持中断，另测触发沿和消抖）。不得把板载 **5 V 电源指示灯**当软件可控 LED。
4. 验收：引脚电平与配置一致，复位和上电没有危险瞬态；NSH 控制台和已验证功能保持可用。记录仪器测量值和采用的实际设备/API 名称，而非假定设备节点固定存在。

## 3. 按键：只在接线可证明时启用

1. 板卡资料中的 **Reset 键用于复位**，不应当成普通 GPIO 用户键。**BOOT 键控制下载模式**；未核对原理图上的连接、上拉、启动采样逻辑和运行时 GPIO 可用性前，不把它注册成普通按键，也不在启动阶段改变其电平。
2. 如原理图证明有可用的独立板载按键，或使用符合 3.3 V 规范的 J1 外接按键，记录引脚、极性、上下拉、消抖和唤醒/中断能力。仅在芯片 GPIO 和 NuttX 按键接口可用时增加注册，优先先验证轮询输入，再单独测试中断。
3. 测试短按、长按、重复按和复位；观察误触发、抖动及 NSH 是否受干扰。无安全的用户键时标注“不支持板载用户按键”，**不为完成清单而复用 Reset/BOOT**。

## 4. MicroSD：卡槽和 4-bit 模式

1. 资料确认本板有 MicroSD 卡槽，支持 4-bit 模式；**并未给出**本 PCB 的 CMD、CLK、D0～D3、卡检测、上拉、供电/电压和复位时序。先从目标参考设计记录这些信号及与其他功能的复用冲突；核对电源域与 `LDO_VO3/LDO_VO4` 的责任。
2. 确认实际 P4 SD/MMC 控制器驱动、块设备与所选文件系统在当前分支可用；配置卡槽/总线后先验证卡插入与识别、容量、只读分区/目录列举。设备路径和挂载命令以实机枚举和所选文件系统为准，不预写固定 `/dev/mmcsd*` 或自动格式化命令。
3. 以**可擦写的测试卡且已备份数据**为条件，再做小文件写入、同步、重新挂载和校验。分别验证无卡上电、运行时拔插（若硬件/驱动支持）、复位后重新识别；不得把热插拔或 4-bit 性能当成仅靠卡槽资料就已实现。
4. 验收：有卡读写与数据校验正常，无卡仍可进入 NSH；测试过程没有格式化用户卡，也不覆盖板载 16 MB 启动 Flash 的映像区域。

## 5. USB：先分清接口，再选择 Device 或 Host

1. 先依据 **P4X 对应版本参考设计**分别识别 USB Serial/JTAG 下载/调试接口、USB 全速接口和 USB 2.0 OTG/Host 接口的控制器、连接器与供电。USB Serial/JTAG 能烧录或看日志，**不等于** NuttX USB Device/Host 驱动已可用。若 Type-C Device 与 Type-A Host 共享 OTG 资源，按参考设计二选一配置与测试，禁止未经验证同时连接/启用。
2. Device 路径：确认当前 P4 USB 控制器、PHY、设备栈及选择的最小设备类均可用；核对供电、角色检测和枚举接口，接入板级初始化后在主机侧检查枚举、插拔重连与复位，保留独立于被测 USB 功能的 NSH 日志通路。设备类及配置符号必须从当前源码选择，不能仅凭插线显示供电就视作 USB 通信成功。
3. Host 路径：先从原理图确认 Type-A VBUS 电源开关 **TPS2051C** 的控制/故障引脚、极性和 5 V 供电；资料说明对外供电限流约 **500 mA**，测试负载须在已确认供电能力以内。只有在 P4 Host/PHY/电源开关驱动均可用后，才启用 VBUS 并接低功耗已知 USB 设备，验证插拔、枚举、故障恢复及复位后的 VBUS 默认状态。
4. 验收：所选角色能稳定枚举及重连，不会破坏阶段 A 的下载与 NSH 通路；未验证的一侧、其他 USB 连接器和更高功耗设备不标记为支持。若供电或故障信号不明确，Host 路径停在核查阶段。

## 6. 以太网：IP101GR + P4 EMAC RMII

1. 以本板原理图确认 MAC 与 **IP101GR** 的 RMII 信号/复用、参考时钟的方向与频率、PHY 地址的硬件绑带、MDIO/MDC、PHY 复位和中断、供电及电源域；不要套用 C6 或其他 P4 板的地址和时钟设置。
2. 核对 P4 EMAC 控制器、IP101GR 兼容的 PHY 驱动、网络栈及其配置项；需要的公共驱动缺失时走独立上游流程。板级代码只承担本板引脚、电源、复位时序和设备注册，并检查初始化错误码。PHY 未探测成功时先查看 MDIO 读数、时钟/复位/供电，不将网络配置错误误判为引脚错误。
3. 分层测试：① 无网线启动仍进入 NSH；② 网线插入后观察 PHY ID 和链路建立；③ 配置隔离测试网络的地址、网关等参数（按实测接口名及当前栈选择 DHCP 或静态地址）；④ 与受控主机互通并检查收发；⑤ 断开/重新插入网线、复位和冷启动后重新获得链路。
4. 验收：PHY 识别、链路状态、数据收发各有日志或测试记录，NSH 不被阻塞。DHCP 服务、PHY 中断线或网络环境缺失时分别标记原因，不因“插上网线 LED 亮”就宣称以太网通过。

## 7. 每项回归、变更记录及阶段 B 验收

每次仅启用一个新功能后，使用阶段 A **同一条已验证**的构建/烧录/控制台路径，确认生成配置保留了该功能与 NSH 的必需选项、源文件实际编译链接；实机至少完成冷启动、Reset 复位、NSH 输入/输出和先前已通过外设的回归。对于卡拔插、USB 断连、以太网拔线等**可预期的缺席**场景，应避免整机卡死或丢失控制台，并保存错误信息。涉及文件写入、网络联机与 VBUS 供电的测试前，应先确认测试介质、隔离网络和外设额定电流。

建议 README/测试记录逐项填写：功能与状态（通过/失败/阻塞/未测）、PCB 版次、原理图页码、芯片及驱动版本、配置差异、初始化入口、实际引脚/电源/时钟、测试用设备、命令/日志、回归结果、已知限制。功能项只有满足其各自验收条件才能标记“已适配”；没有硬件依据或当前 P4 驱动时保持“阻塞”，不以其他开发板的代码示例代替实机验证。

- [ ] 阶段 A 的可交互 NSH 基线已经通过并留有冷启动与复位日志。
- [ ] 至少一项基础外设完成“硬件依据 → 驱动依据 → 板级接入 → 实测 → 回归”的完整闭环；其余按真实状态列出。
- [ ] GPIO 没有占用串口/启动管脚或误把 5 V LED 当软件 LED；Reset/BOOT 没有被误认作普通用户键。
- [ ] MicroSD 不覆盖启动 Flash，不对用户介质做无同意的格式化/写入；USB 角色与 VBUS 供电符合本板实际连线；以太网 PHY 参数有原理图和实测依据。
- [ ] 每项新增功能后冷启动、复位与控制台均无退化；公共芯片/驱动改动没有混入队伍板级目录。
